Eje Temático: Análisis y Modelado Orientado a Objetos con UML ​

🧭 Introducción: El Plano de la Construcción de Software ​

Así como un ingeniero civil o arquitecto no comienza a vaciar concreto sin antes haber dibujado los planos estructurales, eléctricos e hidráulicos de un edificio, un ingeniero de software no debe codificar sin haber modelado previamente la estructura y el comportamiento del sistema.

El Lenguaje Unificado de Modelado (UML - Unified Modeling Language) es el estándar gráfico universal de la ingeniería de software (mantenido por el Object Management Group - OMG). En el PST II, UML permite que los estudiantes comuniquen visual y técnicamente cómo interactúan los usuarios con el sistema, cómo viajan los datos y cómo se estructuran los objetos en el código.

🏛️ CAPÍTULO I: Los Tres Tipos de Modelos en UML ​

UML cuenta con 14 tipos de diagramas oficiales, pero en el alcance del PST II se dominan con profundidad cuatro diagramas esenciales:

🎭 CAPÍTULO II: Diagrama de Casos de Uso (DCU) ​

El Diagrama de Casos de Uso modela el comportamiento del sistema desde el punto de vista del usuario exterior. Responde a: ¿Quién usa el sistema y qué metas u objetivos puede alcanzar?

2.1 Elementos del Diagrama ​

  • Actor: Rol que juega una persona, organización o sistema externo que interactúa con la aplicación (ej: Administrador, Operador, Jefe de Familia).
  • Caso de Uso (Óvalo): Representa una unidad de funcionalidad coherente que produce un resultado observable de valor para el actor (ej: Registrar Habitante, Emitir Constancia, Consultar Inventario).
  • Límite del Sistema (Rectángulo): Delimita el alcance de la aplicación informática frente al mundo exterior.

2.2 Relaciones entre Casos de Uso ​

  1. Asociación: Línea continua entre un actor y un caso de uso.
  2. <<include>> (Inclusión): El caso de uso base incorpora obligatoriamente el comportamiento de otro caso de uso para completarse.
    • Ejemplo: Registrar Paciente <<include>> Validar Cédula en BD.
  3. <<extend>> (Extensión): El caso de uso añade comportamiento al caso base solo bajo ciertas condiciones opcionales o excepcionales.
    • Ejemplo: Emitir Receta <<extend>> Generar Alerta de Alergia a Medicamento.

2.3 Plantilla Estándar de Especificación Textual de Caso de Uso ​

Todo óvalo del diagrama debe estar acompañado de su ficha textual descriptiva:

CampoDetalle
ID y Nombre:CU-01: Registrar Nuevo Habitante
Actor Principal:Operador del Consejo Comunal
Propósito:Almacenar los datos de un habitante en la base de datos para incorporarlo al censo digital.
Precondición:El operador ha iniciado sesión en el sistema y tiene permisos de escritura.
Flujo Básico (Feliz):1. El operador ingresa al módulo 'Habitantes' y presiona 'Nuevo'.
2. El sistema muestra el formulario.
3. El operador ingresa cédula, nombres, fecha de nacimiento y dirección.
4. El operador presiona 'Guardar'.
5. El sistema valida los datos y almacena el registro.
6. El sistema muestra mensaje de confirmación exitosa.
Flujos Alternativos / Excepciones:4a. Cédula ya registrada: El sistema muestra alerta 'La cédula ya existe' y no guarda.
4b. Campos obligatorios vacíos: El sistema resalta en rojo los campos requeridos.
Postcondición:El habitante queda registrado activamente en el censo comunitario.

⚡ CAPÍTULO III: Diagramas de Comportamiento: Actividades y Secuencia ​

3.1 Diagrama de Actividades ​

Modela el flujo de trabajo paso a paso de un proceso de negocio o algoritmo. Es ideal para mostrar cómo se coordinan las decisiones y las acciones entre el usuario y la computadora. Utiliza carriles (swimlanes) para separar responsabilidades.

3.2 Diagrama de Secuencia ​

Modela cómo colaboran los objetos en el tiempo para ejecutar un caso de uso, mostrando el intercambio de mensajes entre la interfaz de usuario (Vista), la lógica de negocio (Controlador) y la base de datos (Modelo).

🧱 CAPÍTULO IV: Diagrama de Clases del Dominio ​

El Diagrama de Clases es el modelo estructural por excelencia. Representa las clases del sistema, sus atributos privados/públicos, sus métodos y las relaciones estáticas entre ellas.

4.1 Tipos de Relaciones entre Clases ​

  • Herencia (Generalización): Una clase hija hereda atributos y métodos de la clase padre (Habitante es una Persona).
  • Asociación: Relación estructural simple entre dos clases con multiplicidad (1..*, 0..1).
  • Agregación: Relación "todo-parte" débil. Las partes pueden existir sin el todo.
  • Composición: Relación "todo-parte" fuerte. Si se destruye el objeto principal, las partes también desaparecen (si se elimina una factura, se eliminan sus renglones de detalle).

📝 Conclusiones y Entregables de la Evaluación 2 ​

Para la Evaluación 2 del Trimestre V, el equipo presentará el Dossier de Modelado UML:

  1. Diagrama de Casos de Uso General del Sistema y especificaciones textuales completas.
  2. Diagramas de Actividades de los procesos más complejos (ej: emisión de documentos o cálculos de inventario).
  3. Diagrama de Secuencia de los flujos críticos (autenticación y guardado transaccional).
  4. Diagrama de Clases del dominio del problema debidamente tipificado.
